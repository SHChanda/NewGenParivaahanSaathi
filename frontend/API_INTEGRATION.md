# Sarathi Next API Integration

The formal contract is [openapi.yaml](./openapi.yaml). The frontend calls the API through the same-origin gateway at `/api/backend/*`; the gateway forwards requests to `SARATHI_API_BASE_URL`.

## Environments

| Environment | Configuration |
|---|---|
| Local | Copy `.env.example` to `.env.local` and set `SARATHI_API_BASE_URL`. |
| Sites production | Add `SARATHI_API_BASE_URL` as a runtime environment variable. Add `SARATHI_API_KEY` as a secret only if the backend requires service-to-service authentication. Redeploy after changing runtime variables. |
| No backend configured | The frontend retains the current mock prototype behavior. |

The API base URL should be the origin only, for example `https://api.example.com`. Contract paths already include `/v1`.

## Request path

```text
Browser
  → /api/backend/v1/...
  → Sarathi Next server gateway
  → SARATHI_API_BASE_URL/v1/...
```

Do not place API keys, Aadhaar-provider secrets, SMS credentials, or signing credentials in browser code or variables prefixed with `VITE_` or `NEXT_PUBLIC_`.

## Authentication

- OTP verification responses create an HttpOnly, Secure, SameSite=Lax cookie named `sarathi_session` with `Path=/` and no `Domain` attribute. This lets the same-origin gateway store it for the Site host.
- The gateway relays the cookie between the browser and API server.
- The backend must authorize every application operation against the session.
- Never authorize a request solely from the `applicationId` supplied by the browser.
- Aadhaar and OTP values must not appear in logs or response payloads after verification.

## Standard headers

| Header | Direction | Purpose |
|---|---|---|
| `Content-Type` | Both | JSON or multipart content type |
| `Accept` | Request | Expected response type |
| `Idempotency-Key` | Request | Required for create, hold, confirm, sign, submit, and payment-like operations |
| `X-Request-ID` | Both | Correlation identifier |
| `Retry-After` | Response | Backoff duration for throttling or temporary unavailability |
| `Set-Cookie` | Response | Establish or refresh `sarathi_session` |

## Error format

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Check the highlighted fields.",
    "fieldErrors": {
      "mobileNumber": "Enter a valid 10-digit mobile number."
    },
    "requestId": "req_01J..."
  }
}
```

Expected codes include `VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `OTP_EXPIRED`, `OTP_INVALID`, `RATE_LIMITED`, `SLOT_UNAVAILABLE`, `HOLD_EXPIRED`, `DOCUMENT_TOO_LARGE`, `UNSUPPORTED_MEDIA_TYPE`, and `INTERNAL_ERROR`.

## File handling

- Age proof: image or PDF, maximum 500KB.
- Address proof: image or PDF, maximum 500KB.
- Applicant photo: image only, maximum 500KB. Mobile browsers may capture it with the front-facing camera.
- Mock signature is generated by the frontend; the backend records the signing action rather than requiring a real signature upload.
- Scan and validate files server-side even though the browser validates them first.
- Do not return storage bucket paths or internal object keys to the browser.

## Backend readiness

Implement endpoints incrementally. The frontend treats `503 API_NOT_CONFIGURED`, `501 NOT_IMPLEMENTED`, and network-unavailable responses as mock-mode signals. Other API errors are shown to the user and are not silently replaced with mock success.

## Private API option

If the API is only reachable inside a private network, publish the Site with a private HTTP tunnel binding instead of exposing the server publicly. Server code receives the binding as `CUSTOMER_HTTP_<UPPER_ALIAS>`.
